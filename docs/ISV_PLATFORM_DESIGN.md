# 第三方应用接入：产品设计方案 v1.0

> 面向：产品 / 运营 / 研发内部对齐使用
> 状态：方案待评审，代码仅部分落地（见第 7 章状态列）
> 日期：2026-11-02

---

## 1. 设计目标

### 1.1 一句话

> 让**任何形态**的第三方应用，用**同一套规则**，把数据安全地显示到用户的墨水屏上，而平台永远不接触用户的账号凭证。

### 1.2 适用范围

关键前提：**不是只为「GitHub 工程导入」这类开发者设计的**。以下所有形态都走同一套协议：

| 形态 | 举例 | 是否支持 |
|---|---|---|
| 桌面应用（macOS / Windows） | Codex 脉动 | ✅ |
| 移动 App | 记账、健身 | ✅ |
| 小程序 | 微信/支付宝小程序 | ✅ |
| 网页应用（纯前端） | 静态站、SaaS 控制台 | ✅ |
| 服务端 / 后端 API | 企业自建系统 | ✅ |
| 命令行工具 / 脚本 | CLI、自动化 | ✅ |
| 硬件设备 | 其他品牌的传感器 | ✅ |

**唯一的门槛不是技术形态，而是能不能按契约输出数据。**

### 1.3 三条不可让步的原则

| # | 原则 | 如果让步会怎样 |
|---|---|---|
| 1 | **用户必须显性点击授权，不可静默** | 违反个保法单独同意，平台承担连带责任 |
| 2 | **平台不存任何第三方凭证** | 一次库泄露 = 全部用户账号被盗 |
| 3 | **数据库不互通，只走 API** | 无法审计、无法限流、一方改表全崩 |

## 2. 角色与分层

### 2.1 三层模型

```
第一层 确权  →  这条数据是谁的、该上哪块屏
第二层 业务  →  数据从哪来、长什么样、多久更新
第三层 渲染  →  A 屏显示什么、B 屏显示什么
```

严格顺序依赖：没确权 → 推送被拒；没契约 → 审核打回；没双屏设计 → 设备显示不全。

### 2.2 三方职责矩阵

| 能力 | 平台 | 用户 | 开发者 |
|---|---|---|---|
| 签发/校验授权 | ✅ 独占 | — | — |
| 决定是否授权 | — | ✅ 独占 | — |
| 持有大模型凭证 | ❌ 永不 | ✅ 独占 | 代用户使用（不转存） |
| 取数 | 仅自有数据 | — | ✅ |
| 渲染出图 | ✅ 独占 | — | 设计内容 |
| 撤销授权 | 提供入口 | ✅ 执行 | — |

### 2.3 平台能力边界（明确不做的事）

写清楚“不做什么”比写“做什么”更重要，避免销售/运营对外承诺错：

| 不做 | 原因 |
|---|---|
| 代查用户任何大模型余额 | 无开放接口；需持有用户 token，风险不可接受 |
| 跨应用抓数据拼一屏 | 越权；每个应用只能动自己被授权的那部分 |
| 托管第三方 API Key | 泄露即灾难 |
| 直连开发者数据库 | 无法审计、无法限流 |
| 为开发者代持用户账号密码 | 同上 |

## 3. 接入形态矩阵

### 3.1 四种终端 × 两种投递

终端形态决定**确权的码怎么给用户看**，投递模式决定**数据怎么上来**，两者正交：

| 终端 | 确权方式 | 推荐投递 | 说明 |
|---|---|---|---|
| 桌面应用 | 应用内显示 6 位码，用户去后台输 | **Push** | 在家用 NAT 后，平台无法访问 |
| 移动 App | 内嵌授权页或跳转 | Push / Pull | 看是否有自有云 |
| 小程序 | 直接调起授权页 | Push / Pull | 体验最好 |
| 网页 | 直接跳授权页 | Pull 居多 | 有公网域名 |
| 服务端 | 后台配置页显示码 | **Pull** | 通常有公网服务 |
| CLI | 终端打印码 + 短链 | Push | — |

### 3.2 推荐的默认组合

| 开发者类型 | 默认方案 |
|---|---|
| 个人开发者 / 桌面工具 | 码 + Push |
| 有 SaaS 的团队 | 码 + Pull |
| 平台自有内容（天气等） | 无需接入，平台内置 |

**设计决策：Push 优先。** 因为最典型的接入方（桌面工具）只能 Push；Pull 作为补充能力，不做强制。

## 4. 确权设计

### 4.1 状态机

```
        ┌─────────┐  用户点「拒绝」  ┌────────┐
        │ pending ├────────────────→│ denied │
        └────┬────┘                 └────────┘
             │ 用户点「允许」
             ↓
        ┌─────────┐  用户撤销   ┌─────────┐
        │ active  ├───────────→│ revoked │
        └─────────┘             └─────────┘

        pending 超过 10 分钟 → expired（需重新申请）
```

规则：

- 一个码只能被确认一次，确认后立即失效
- 撤销后**不会自动恢复**，必须用户重新授权
- 同一 `(app, device)` 只有一条有效授权，重新授权复用同一行

### 4.2 授权页设计（平台统一提供）

**一个页面，三端复用**（小程序 webview / PC 后台 iframe / 手机浏览器直开）。这是“通用”的落地点，不允许三端各写一套。

页面必须包含的字段：

| 位置 | 内容 | 为什么必须 |
|---|---|---|
| 标题 | 「Codex 脉动 申请接入」 | 用户要知道是谁 |
| 应用信息 | 图标 + 名称 + 开发者名 | 防冒名 |
| 权限说明 | 「向你的设备推送显示内容」（人话） | 不能只写 scope 名 |
| 目标设备 | 设备名 + 型号 + device_id 后 4 位 | 用户要知道上哪块屏 |
| 风险提示 | 「该应用由第三方提供，数据由对方负责」 | 责任划分 |
| 操作 | 【拒绝】【允许】 | 必须二选一，不可默认 |
| 有效期 | 「长期有效，可随时在『已授权应用』撤销」 | 消除顾虑 |

**禁止**：默认勾选、倒计时自动通过、扫码即授权、把「允许」做成主色调诱导。

### 4.3 用户侧：已授权应用管理

入口：小程序「我的」+ PC 后台「我的设备」。

列表每项显示：应用名 / 授权时间 / 关联设备 / 最后推送时间 / 【撤销】。

撤销后：对方下次推送返回 `403 grant_revoked`，并触发一次通知给开发者（可选）。

### 4.4 运营侧：授权治理

运营后台需要看到：

| 视图 | 用途 |
|---|---|
| 授权总量 / 按应用 | 判断哪个应用在被真实使用 |
| 异常推送（高频/失败率） | 发现滥用 |
| 一键全局撤销（按应用） | 应用出问题时紧急止血 |
| 下架应用 | 连带撤销其全部授权 |

### 4.5 失效与边界

| 场景 | 行为 |
|---|---|
| 用户解绑设备 | 该设备全部授权自动失效 |
| 应用被下架 | 全部授权失效，推送 403 |
| App Key 重置 | 旧 key 立即失效，授权关系保留 |
| 设备换主人 | 新用户需重新授权 |

## 5. 数据契约（摘要）

字段级细节见 `docs/ISV_INTEGRATION_PROTOCOL.md`，这里只列设计决策。

### 5.1 卡片结构

```jsonc
{
  "title": "≤24 字",
  "subtitle": "≤32 字",
  "items": [ { "label": "≤12", "value": "≤16", "progress": 0-100, "emphasis": "red|yellow" } ],
  "footer": "≤40 字",
  "qr": "可选，绝对 URL"
}
```

硬约束：`items` 最多 6 项（建议 4）、总大小 ≤32KB、百分比取整。

### 5.2 双屏语义

| 屏 | 回答 | 内容 |
|---|---|---|
| A | 我现在还有多少 | 主指标、是否告警 |
| B | 接下来会怎样 | 倒计时、趋势、预计耗尽 |

**判定：两屏内容不许重复。**

### 5.3 设计决策：为什么不让开发者交 HTML

固件不跑浏览器，只显示服务端生成的位图。若允许交 HTML，需要无头浏览器栅格化，成本高、样式不可控、审核困难。**交结构化数据是唯一可规模化的路径。**

## 6. 审核与治理

### 6.1 三道关

| 关 | 检查 | 自动/人工 |
|---|---|---|
| 一、自动校验 | 契约字段、尺寸、字号、payload 大小、凭证声明完整性 | 自动 |
| 二、实机预览 | A/B 双屏出图，看截断、配色、语义重复 | 人工 |
| 三、合规复核 | 数据来源说明、是否涉及第三方凭证、隐私边界 | 人工 |

### 6.2 打回的高频原因（用于培训审核）

1. B 屏只是重复 A 屏
2. `value` 超 16 字符被截断
3. 取数失败时推 0 或 `--` 冒充真实值
4. 未声明数据来源
5. 推送频率过高（< 1 分钟）
6. A 屏用了红色（硬件不支持）

### 6.3 下架条件

- 伪造数据、推送与声明不符
- 越权访问设备
- 出现隐私泄露事件
- 连续 30 天零推送且联系不上

## 8. 联调流程

### 8.1 环境

| 环境 | 用途 | 数据 |
|---|---|---|
| 开发者本地 | 自测 | 自己的测试设备 |
| 沙箱环境 | 联调 | 平台分配的测试设备 |
| 生产 | 上线 | 真实用户 |

### 8.2 双方分工

| 阶段 | 开发者 | 平台 |
|---|---|---|
| 确权联调 | 实现申请码 + 轮询 | 确保码能签发、确认能落库 |
| 推送联调 | 构造卡片 JSON | 确认 202 + 设备能拉到 |
| 出图联调 | 提供真实数据 | 出 A/B 预览图，双方看同一张图 |
| 真机验收 | — | 提供实拍图或视频 |

### 8.3 验收标准（四条全过才算联调完成）

1. 用户能独立走完授权，无需开发者远程协助
2. 撤销后 1 分钟内推送被拒
3. A/B 两屏在真机上无截断、无重叠、语义不重复
4. 断网 / 取数失败时，屏上显示的是「说明」而不是假数据

## 9. 风险与未决问题

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | 用户不知道 `device_id`，怎么在授权页选设备 | 体验断层 | 授权页只列该用户已绑定设备，不给自由输入 |
| 2 | 一个设备被多个应用授权，谁的内容优先 | 冲突 | v1 按场景人工编排；v2 做优先级 + 轮播 |
| 3 | 应用被恶意仿冒（同名不同开发者） | 信任 | 授权页强制显示开发者名 + 认证标识 |
| 4 | 开发者拿到 device_id 后能否反查用户 | 隐私 | 平台接口不返回 user_id，只返回 device_id |
| 5 | 是否需要给开发者推送回执 | 运维 | 建议做，便于对方确认出图成功 |
| 6 | 多应用同屏合成 | 产品想象空间 | 明确列为 v2，避免现在过度设计 |
