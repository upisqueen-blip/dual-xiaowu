# 森穹小悟双屏 · 产品定义 v2 与优化路线

> 输入：外部评审意见（双后台/双站点视角）
> 用途：产品与研发对齐；对外可用于给合作方解释"我们做什么、不做什么"
> 日期：2026-11-11

---

## 0. 结论先行

评审意见**方向和直觉是对的**：降低接入摩擦、补新手引导、把"两点一线"的用户路径讲清楚。但它的事实层有 5 处过时或错位，若照单全收排期，会做掉 2~3 周无效功。

| # | 评审判断 | 实际 | 影响 |
|---|---|---|---|
| 1 | 场景模板只有天气+小悟今日，需补 4 套 | 已有 7 套预设，含 Token 余额、作业便签、行情快照、饮水提醒 | 不用补模板，要补**推荐位和对比** |
| 2 | 需防止用户填 1 秒刷新烧屏 | UI 只有 6 档下拉，最短 5 分钟，填不了 1 秒 | **真 bug 是：用户选了什么后端都不看** |
| 3 | Webhook 调试面板是王牌，放 P0 | 现有 webhook 是**出站**订阅，且投递 worker 未实现 | 打错管子，P0 会空转 |
| 4 | 需做离线兜底、保存最后一帧 | 墨水屏物理双稳态，断电即保持画面 | 不存在这个需求 |
| 5 | 需做可视化拖拽布局编辑器 | 无此功能 | 建议**明确不做**，是无底洞 |

**三条核心结论**

1. 用户后台缺的不是功能，是**一条被验证过的首次路径**（现在 7 套场景 30+ 模块，新用户选不出来）。
2. 开放平台缺的不是调试面板，是一条**「一条 curl 就能上屏」的窄门**——现在推内容必须先注册开发者应用、拿 App Token、走模板校验、完成设备与应用配对，个人 Agent 用户在第一步就流失。
3. 「Webhook 更省力」这句判断成立，但要落到**入站直推**上，而不是给现有出站 webhook 加日志。

## 1. 逐条核验

事实列均可对应到代码位置，便于研发复核。

| 评审项 | 评审判断 | 代码现状 | 判定 |
|---|---|---|---|
| 新手引导 | 缺任务流，新用户不知道先干什么 | 有「配置引导」页，是静态流程图 SVG；空态只引导"绑定第一台设备" | ✅ 采纳，改为可勾选 4 步 |
| A/B 屏术语 | 后台写 FPC1/FPC2，普通人看不懂 | 用户后台已是「A 屏 / B 屏 + 尺寸 + 色数」（`panelColorName`）；FPC 只出现在文档与固件 | ⚠️ 用户侧已改，但**术语三处不一致**，需统一词表 |
| 场景模板 | 只有天气+小悟今日，缺 4 套核心模板 | `presetScenes` 已 7 套：系统/家庭/学习/理财/养生/办公/自由组合，办公即含 Token 余额 | ❌ 事实过时。问题是"太多且无推荐" |
| 刷新频率保护 | 防止用户填 1 秒，加安全上限 | 下拉 6 档：5/10/15/30 分、12/24 小时 | ⚠️ 伪需求。**但** `render_api.py:266` 写死 `A=5 / B=30`，用户选择完全不生效 |
| 同步反馈 | 只有"待上线"，不知是否下发成功 | 保存/下发只有 toast；设备表有 `last_seen_at`，**无 `last_render_at`** | ✅ 采纳，补状态机 + 最后出图时刻 |
| 两类人群入口 | 普通用户与开发者入口混在一起 | 两个独立域名已分离，但互相没有门牌 | ✅ 轻度采纳，各加一句话分流 |
| JSON 沙箱示例 | 缺示例 JSON，新人不知写什么 | 后端已有 `/api/preview` 与 `try_render`，做即时渲染成本低 | ✅ 采纳，且不必新建渲染链路 |
| Webhook 调试 | P0，日志+重放+HMAC | webhook 仅出站订阅（`/openapi/v1/webhooks`），`docs/04-openapi` 自述"投递 worker、重试、HMAC 属下一迭代" | 🔴 方向对、对象错。缺的是**入站推送地址** |
| 创作者规则 | 无审核/分成说明 | 有提审与审核接口（`/developer/v1/apps/submit`、`/admin/v1/developer-submissions`），无规则文档 | ⚠️ 有流程无契约 |
| 可视化编辑器 | 中期补，降低内容创作者门槛 | 无 | 🟡 建议不做，见 §4 |
| 金融监管 | 禁止实时行情与买卖信号 | 已有理财场景（自选行情，5/10 分钟） | ⚠️ 风险在**行情数据源授权**，不在投顾资质 |
| 离线兜底 | 保存最后一帧 | 墨水屏断电即保持画面 | ❌ 伪需求。真问题是断网后仍每小时硬刷 |
| 多设备 | 支持一账号多台 | 已支持设备列表与共享成员 | ✅ 已有 |

## 2. 产品定义 v2

### 2.1 一句话

> 森穹小悟是给**已经在用 AI 的人**一块不打扰的状态副屏：复杂逻辑留在你自己的电脑、Dify、Coze 或自建服务里，屏幕只负责把「此刻最重要的一条状态」安静地亮出来。

### 2.2 三个"不做"

写清不做什么，比写做什么更能约束研发和销售：

| 不做 | 原因 |
|---|---|
| 不在屏上跑 Agent、不做对话 | 刷新一次 20~30 秒，交互模型不成立 |
| 不做实时行情、不做秒级刷新 | 硬件物理限制；且行情源授权成本高于收益 |
| 不做通用电子纸开发板 | 开源边界已划（`docs/hardware-boundary.md`）；先服务两个具体人群 |

### 2.3 三层用户，两条管道

这是本次最需要改的结构：**中间那层人是空的**。

| 层 | 是谁 | 他要什么 | 唯一入口 | 成功标准 | 现状 |
|---|---|---|---|---|---|
| L0 开箱用户 | 家长、送礼、老人 | 插电就有内容，不配置 | 用户后台场景中心 | 10 分钟内出第一屏 | 有，但路径太长 |
| **L1 Agent 玩家** | 用 Dify/Coze/Claude Code/自建脚本 | 一条 curl 把输出推上屏 | 设备详情页「推送地址 + Token」 | 5 分钟内收到自推内容 | **完全没有** |
| L2 开发者/ISV | GitHub 项目、SaaS、行业方案 | 可分发、可审核、可收费 | 创作者开放平台 | 提审→上架→被安装 | 有骨架，规则缺失 |

两条管道必须分开，共用渲染层：

```
                        ┌──────────────────────────────┐
  L0 后台配场景  ───────▶│                              │
                        │   渲染层 render.py           │──▶ A 屏（文字/状态）
  L1 设备直推    ───────▶│   同一套版式 / 同一套色数     │──▶ B 屏（彩色/海报）
  POST /push/<token>    │                              │
                        │                              │
  L2 App / ISV   ───────▶│  仅 L2 走模板校验 + 作用域    │
  /openapi/v1/...       └──────────────────────────────┘
```

- **L1 设备直推（新增）**：每台设备一个 `POST /push/<device_token>`，请求体固定三种版式之一（`list` / `big-number` / `notice`），不需要注册应用、不需要模板、不需要审核，用户在后台开关授权、可随时撤销。这一步对齐 `docs/ISV_PLATFORM_DESIGN.md` 的"用户必须显性授权"原则，不破坏确权模型。
- **L2 保持不变**：继续走 `/openapi/v1`、模板校验、提审、上架。这是给要分发的第三方用的，不是给个人玩家用的。

### 2.4 边界文案（对外统一，三处复用）

> ✅ 适合：Agent 任务状态、Token 余额、待办与打卡、定投快照、作息提醒，分钟到小时级更新
> ❌ 不适合：实时对话、秒级行情、本地大模型推理

投放位置：商品页、用户后台首页、创作者平台首页。

## 3. 优化清单

### P0 · 两周内（直接影响第一批用户）

| # | 事项 | 具体做法 | 验收标准 |
|---|---|---|---|
| 1 | **修刷新不生效** | `render_api` 从 `dual_config` 读 A/B 各自 `refresh`，服务端 clamp 到 [2, 1440] 分钟再写 `X-Refresh-Minutes`；UI 拆成 A/B 两个下拉 | 设 30 分钟 → 响应头 30 → 设备 `clr_ref_min`(30)；设 1 分钟被 clamp 到 2 |
| 2 | 新手 4 步任务条 | 总览页顶部：绑设备 → 选场景 → 设刷新 → 下发；有勾选态与"下一步" | 新账号从登录到出第一屏 ≤ 4 次点击 |
| 3 | 离线自检卡 | 离线时展开 3 项（通电 / WiFi / 固件版本 vs 最新）+「重新唤醒」；新增 `last_render_at` 显示"屏最后更新于 X 分钟前" | 拔电后卡片给出可执行结论，不是只显示"离线" |
| 4 | **L1 设备直推上线** | 设备详情 → 推送地址 + Token + 一行 curl 示例 + 撤销开关；固定 3 种版式 | 复制 curl 到终端，2 秒内屏幕更新；文案总长 ≤ 20 行 |
| 5 | 统一边界文案 | 见 §2.4 | 三处文案一字不差 |

### P1 · 1~2 个月

| # | 事项 | 说明 |
|---|---|---|
| 6 | L1 推送日志 | 最近 20 条 + 返回码 + 一键重放。**这才是"webhook 调试面板"该有的形态**，挂在直推上而非出站订阅上 |
| 7 | 场景中心重构 | 从 7 张平铺改为「推荐 4 + 更多 3」，每卡带 A/B 双屏缩略图与刷新代价（次/天） |
| 8 | 创作者中心规则 | 提审 SLA、沙箱限制、免费/付费与分成、早期贡献者权益 |
| 9 | 出站 webhook 补完 | 投递 worker + 重试 + HMAC 签名。现在是半成品，**对外暂不宣传** |
| 10 | 三份 15 分钟教程 | Dify / Coze / Claude Code 各一篇，以 L1 直推为主角 |

### P2 · 3~6 个月

| # | 事项 |
|---|---|
| 11 | 家庭多设备状态墙（一账号 N 台屏统一视图） |
| 12 | 模板市场标签体系：Agent 仪表盘 / 学习 / 家庭 / 行业 |
| 13 | 断网省电：离线时指数退避到 30 分钟，避免每小时硬唤醒 |

### 明确不做

| 事项 | 理由 |
|---|---|
| 可视化拖拽布局编辑器 | 三类创作者里只有"内容创作者"需要，而他们可以直接传图；拖拽排版的边界成本远高于收益 |
| 屏上对话 / 本地推理 | 与刷新物理特性冲突 |
| 通用电子纸开发板适配 | 先做深两个人群，不做宽 |

## 4. 对原排期的评价

| 原排期 | 评价 |
|---|---|
| P0 五项 | 只有 2 项真卡人（刷新失效、无引导）。模板与 1 秒刷新两项是伪需求，可省 1 周 |
| P0 放 Webhook 调试面板 | 错。应先做 L1 直推（约 3 天），再把日志作为 P1 增强。先做面板等于给没人用的出站通道装修 |
| P1 放可视化编辑器 | 危险。这是唯一一项会持续吃掉研发资源且不产生留存的功能，建议直接移出路线图 |
| 整体工作量 | P0 约 2 周（1 人全栈），P1 约 4~6 周。原方案按现状估算会翻倍，因为其中混入了不存在的需求 |

## 5. 风险

| 风险 | 应对 |
|---|---|
| L1 直推成为绕过审核的灰色通道 | 仅限设备所有者本人 Token；限额（N 次/天）；平台侧保留内容留存与封禁能力 |
| 刷新频率调到 2 分钟后屏幕快速老化 | clamp 下限 2 分钟，但 UI 明示"A 屏三色全刷约 25 秒，2 分钟刷新每天约 700 次" |
| 术语三处不一致（FPC1/FPC2 / A·B 屏 / 主副屏） | 本周内出一份术语表，文档、固件日志、开放平台统一到「A 屏（文字状态屏）/ B 屏（彩色海报屏）」 |
