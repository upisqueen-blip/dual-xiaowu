# 小悟第三方应用接入手册 v1.0

> 面向：想要把应用数据显示在小悟电子墨水屏上的开发者
> 阅读时间：15 分钟　｜　预计接入周期：**1～3 天**
> 技术细节（字段级契约、错误码、完整示例）见 `docs/ISV_INTEGRATION_PROTOCOL.md`
> 接口速查（在线 + 可下载）：开发者后台 →「API 文档」，或直接下载 `GET /openapi/isv.json`（YAML / Markdown 同源）

---

## 0. 先判断你属于哪一类

不同形态的应用，接入耐心程度不同，先对号入座：

| 你的应用是 | 确权方式 | 数据投递 | 工作量 |
|---|---|---|---|
| 桌面软件（Mac / Windows） | 应用内显示 6 位码 | **Push** | 小 |
| 手机 App | 内嵌授权页 | Push 或 Pull | 中 |
| 小程序 | 直接调起授权页 | 看有无自有云 | 小 |
| 网站 / SaaS | 后台配置页显示码 | **Pull** | 中 |
| 服务端 / 企业系统 | 后台显示码 | **Pull** | 中 |
| 脚本 / CLI | 终端打印码 | Push | 小 |

**共同点**：无论哪一类，确权都走同一套流程，只是「码怎么给用户看」不同。

## 1. 你能得到什么

| 能力 | 说明 |
|---|---|
| 上屏 | 你的数据以卡片形式显示在用户的墨水屏 A/B 屏 |
| 常驻 | 用户授权后，只要设备在线就能持续显示 |
| 可控 | 你自己决定推什么、多久推一次、什么时候过期 |
| 安全 | 你永远拿不到用户的账号凭证，只拿到一个设备标识 |

你**不能**得到：用户的手机号、邮箱、其他应用数据、任何大模型账号信息。

## 2. 准备清单（开工前先备齐）

### 2.1 账号与资质

| # | 准备项 | 说明 | 必需 |
|---|---|---|---|
| 1 | 开发者账号 | 在开发者中心注册（邮箱 + 密码） | ✅ |
| 2 | 实名信息 | 个人：姓名 + 手机号；企业：公司名 + 统一社会信用代码 | ✅ |
| 3 | **合规承诺书签署** | 在线勾选 + 电子签，承诺不转存用户凭证 | ✅ |

> 合规承诺书不是形式。签署后若被查实转存用户凭证，应用会被立即下架且账号封禁。

### 2.2 应用信息（提交审核用）

| # | 字段 | 要求 |
|---|---|---|
| 4 | 应用名称 | ≤ 16 字，不能与已上线应用重名或高度相似 |
| 5 | 一句话简介 | ≤ 40 字，说清「给用户看什么」 |
| 6 | 详细说明 | ≤ 200 字，含数据来源 |
| 7 | 应用图标 | 512×512 PNG，透明背景 |
| 8 | 归属场景 | 从预设场景选一个（办公 / 家庭 / 学习 …），或申请自定义 |
| 9 | 版本号 | 语义化版本，如 `1.2.0` |
| 10 | 支持机型 | 是否支持四色屏（B 屏）、是否有 A/B 差异 |

### 2.3 技术准备

| # | 准备项 | 要求 | 常见坑 |
|---|---|---|---|
| 11 | App Key 安全存储 | 系统钥匙串 / 环境变量 / 加密配置 | ❌ 硬编码进代码、写进 Git、打进前端 |
| 12 | 出网能力 | 能访问平台 HTTPS 接口 | 企业内网要放行 |
| 13 | 本地配置持久化 | 保存 `device_id` + `grant_id` | 重启丢失后要重新走授权，用户会烦 |
| 14 | 定时/触发机制 | 决定多久推一次（建议 ≥5 分钟） | 推太频会被限流 |
| 15 | 错误重试 | 指数退避，最多 3 次 | 无限重试会被封 |
| 16 | 日志脱敏 | 日志里不出现 App Key / token | 排障时容易手滑打印 |

### 2.4 合规材料（审核必看，最容易漏）

| # | 材料 | 内容要求 |
|---|---|---|
| 17 | **数据来源说明**（1 页） | 数据从哪来：用户本机读取 / 你的服务端 / 第三方 API。逐项写明 |
| 18 | **凭证处理声明** | 明确「不转存、不上传用户凭证」，说明凭证存放在哪、生命周期 |
| 19 | **容错方案说明** | 取数失败、数值未知、设备离线时分别显示什么 |
| 20 | 隐私政策链接（如有） | 网页应用必须提供 |

> 第 17～19 项没有固定格式，写清楚即可。审核最常打回的就是这三项缺失。

## 3. 接入五步

```
Step 1 创建应用拿凭证  →  Step 2 实现确权  →  Step 3 实现取数
                                                    ↓
                              Step 5 提交审核  ←  Step 4 设计双屏
```

### Step 1　创建应用，拿到 App Key（约 30 分钟）

1. 登录开发者中心 → 新建应用
2. 填 2.2 的应用信息
3. 系统生成 `app_id`（如 `app-a1b2c3`）和 **App Key**（只显示一次）
4. 立刻存进安全位置，页面关闭后无法再查看，只能重置

**你需要申请的权限**：

| Scope | 用途 | 建议 |
|---|---|---|
| `device.content.write` | 推送内容 | 必申请 |
| `device.read` | 读设备型号/在线状态 | 建议（用于自适应四色屏） |
| `device.event.read` | 读设备回执 | 可选 |

**通过标准**：能在开发者中心看到自己的应用，状态为「开发中」。

---

### Step 2　实现确权（约半天）

这是整个接入的**第一道门槛**，也是用户信任的来源。

#### 流程

```
① 你的应用调用「申请配对码」→ 拿到 6 位码
② 把码显示给用户（界面 / 终端 / 打印）
③ 用户在【小悟后台或小程序】输入码，选择设备，点「允许」
④ 你的应用轮询「查询结果」→ 拿到 device_id
⑤ 把 device_id 存进本地配置
```

#### 代码（Python 示例）

```python
import time, requests

BASE = "https://<平台地址>"
APP_KEY = "你的 App Key"          # 从环境变量读，不要硬编码

def start_pairing():
    r = requests.post(f"{BASE}/openapi/v1/pairing/start",
                      headers={"X-App-Key": APP_KEY},
                      json={"label": "我的 MacBook",          # 会显示给用户看
                            "scopes": ["device.content.write"]},
                      timeout=10)
    r.raise_for_status()
    p = r.json()
    print(f"请打开小悟小程序，输入：{p['display_code']}")
    return p["code"]

def wait_device(code, interval=3, timeout=600):
    deadline = time.time() + timeout
    while time.time() < deadline:
        r = requests.get(f"{BASE}/openapi/v1/pairing/{code}",
                         headers={"X-App-Key": APP_KEY}, timeout=10)
        s = r.json()
        if s["status"] == "approved":
            return s["device_id"]
        if s["status"] in ("denied", "expired"):
            raise RuntimeError(f"授权失败：{s['status']}")
        time.sleep(interval)
    raise TimeoutError("等待授权超时，请重新申请")
```

#### 注意事项

| 事项 | 说明 |
|---|---|
| `label` 要真实 | 它会显示在用户的授权列表里。写「设备1」用户不敢授权 |
| 码有效期 10 分钟 | 过期要重新申请，不要复用 |
| 只轮询一次流程 | 拿到 `approved` 立刻停止，别一直轮 |
| **拿不到 user_id** | 这是设计如此。你只需要 `device_id` |
| 别自己采集 MAC | 用户设备标识由平台给，你不需要也不应该读网卡 |

**通过标准**：用户能独立完成一次授权，你的程序打印出 `device_id`。

### Step 3　实现取数（1～3 天，取决于你的数据源）

#### 3.1 先明确：数据从哪来

| 数据源 | 谁去取 | 平台需要什么 |
|---|---|---|
| 用户本机文件（如 `~/.codex/auth.json`） | 你在用户机器上读 | 只要结果 |
| 你自己的服务端 | 你的后端取 | 只要结果 |
| 第三方 API | 你带用户授权去调 | 只要结果 |
| 平台自有数据（天气等） | 平台自己取 | 你不用做 |

**平台不关心你怎么取，只关心你输出什么。** 这是你能快速接入的关键。

#### 3.2 组织数据

一张卡片 = 标题 + 最多 6 行数据。以「API 额度」为例：

```json
{
  "title": "API 额度",
  "subtitle": "Codex",
  "items": [
    { "label": "剩余额度", "value": "$42.10", "emphasis": "red" },
    { "label": "到期倒计时", "value": "6 天" },
    { "label": "本月用量", "value": "68%", "progress": 68 }
  ],
  "footer": "本机读取 · 17:08"
}
```

字段速查：

| 字段 | 限制 | 说明 |
|---|---|---|
| `title` | ≤24 字 | 卡片主标题 |
| `subtitle` | ≤32 字 | 来源 / 时间范围 |
| `items` | 1～6 项（建议 4） | 数据行 |
| `items[].label` | ≤12 字 | 指标名 |
| `items[].value` | ≤16 字 | 值，超了会被截断 |
| `items[].progress` | 0～100 | 有则画进度条 |
| `items[].emphasis` | `red` / `yellow` | 仅四色屏有效 |
| `footer` | ≤40 字 | 数据来源、更新时间，**建议写上** |

#### 3.3 推送

```python
def push(device_id, card_a, card_b):
    r = requests.post(f"{BASE}/openapi/v1/devices/{device_id}/content",
                      headers={"X-App-Key": APP_KEY},
                      json={
                          "template": "eink-card-v1",
                          "screens": {"A": card_a, "B": card_b},
                          "expires_in_seconds": 900,   # 15 分钟未更新则回落
                      },
                      timeout=10)
    r.raise_for_status()
    return r.json()          # {"task_id": "...", "status": "queued"}
```

#### 3.4 三条硬规矩

| 规矩 | 原因 |
|---|---|
| 取数失败**不要**推 `0` 或 `--` | 假数据比没数据更害人，用户会误判 |
| 数值未知写 `"待确认"` | 诚实，用户能理解 |
| `expires_in_seconds` 必须设 | 否则一周前的旧余额会一直挂着 |

**通过标准**：能在开发者后台点「设备出图预览」，看到你的真实数据被渲染成 A/B 两屏。

### Step 4　设计双屏（约半天）

#### 分工原则

| 屏 | 回答的问题 | 放什么 |
|---|---|---|
| **A 屏** | 我**现在**还有多少 | 主指标、百分比、是否告警 |
| **B 屏** | **接下来**会怎样 | 倒计时、趋势、下次重置 |

**判定标准：两屏内容不许重复。** 重复了审核一定打回。

#### 正确的例子

| | A 屏 | B 屏 |
|---|---|---|
| 标题 | API 额度 | 重置预告 |
| 内容 | 剩余 $42.10 / 用量 68% | 预计 11-08 重置 / 周期第 3 天 |
| 回答 | 现在还剩多少 | 什么时候恢复 |

#### 错误的例子

| | A 屏 | B 屏 | 问题 |
|---|---|---|---|
| 内容 | 剩余 68% | 已用 32% | 同一件事换个说法，浪费一屏 |

#### 硬约束

| 项 | 限制 |
|---|---|
| 正文字号 | ≥ 18 px（墨水屏 DPI 低，小字糊） |
| 每屏数据行 | ≤ 4 行 |
| 标题长度 | ≤ 12 个中文 |
| 颜色 | A 屏只有黑/白；B 屏黑/白/红/黄 |
| 动画、渐变、阴影 | **禁止** |

**通过标准**：A/B 两屏放在一起，别人一眼能说出「左边是现在，右边是未来」。

### Step 5　自测 + 提交审核

#### 5.1 自测清单（逐项打勾，全过再提交）

**确权**

- [ ] 用户能独立完成授权，我没远程协助
- [ ] 码过期后提示清楚，能重新申请
- [ ] 用户拒绝后，我的程序正确退出，不无限轮询
- [ ] `device_id` 能持久化，重启后不用重新授权
- [ ] 用户撤销授权后，我的推送收到 403 并能提示用户重新授权

**数据**

- [ ] 卡片 JSON 不超过 32KB
- [ ] 所有 `value` 都 ≤16 字符（我实际数过）
- [ ] 取数失败时有降级方案，没推假数据
- [ ] `expires_in_seconds` 设置了合理值

**显示**

- [ ] 用「设备出图预览」看过 A/B 两屏
- [ ] 没有文字被截断
- [ ] A 屏没用红色（硬件不支持）
- [ ] B 屏不是 A 屏的复制品

**合规**

- [ ] 我准备好了数据来源说明
- [ ] 我准备了凭证处理声明
- [ ] 日志里不会打印 App Key

#### 5.2 提交审核

在开发者中心点「提交审核」，系统自动校验格式，然后进入人工审核。

审核看三件事：**数据是否真实、双屏是否有设计、合规是否齐全。**

**通过标准**：状态变为「已上线」，应用出现在用户的「已上线应用」里，带 `ISV提供` 标签。

## 4. 联调阶段双方怎么配合

| 阶段 | 你做什么 | 我们做什么 |
|---|---|---|
| 确权联调 | 实现申请码 + 轮询 | 确保码能签发、确认能落库 |
| 推送联调 | 推一张测试卡片 | 确认返回 202、设备能拉到 |
| 出图联调 | 给真实数据 | 出 A/B 预览图，双方看同一张 |
| 真机验收 | — | 提供实拍图或视频 |

**联调完成的四条标准**：

1. 用户能独立走完授权
2. 撤销后 1 分钟内推送被拒
3. 真机上无截断、无重叠、两屏不重复
4. 断网时显示的是说明，不是假数据

## 5. 常见打回原因（Top 8）

| # | 原因 | 怎么改 |
|---|---|---|
| 1 | B 屏只是重复 A 屏 | 换成「未来/趋势/倒计时」 |
| 2 | `value` 超 16 字被截断 | 缩短或改成缩写 |
| 3 | 取数失败推了 0 | 改成「待确认」或推说明卡 |
| 4 | 没写数据来源 | 补 1 页说明 |
| 5 | 推送太频繁（< 1 分钟） | 降到 ≥ 5 分钟 |
| 6 | A 屏用了红色 | 改黑色加粗 |
| 7 | `label` 写成「设备1」 | 写真实设备名 |
| 8 | App Key 出现在前端代码里 | 移到服务端 |

## 6. 上线后你要维护什么

| 责任 | 说明 |
|---|---|
| 数据准确性 | 你推什么，用户就看到什么。推错由你负责 |
| 故障响应 | 连续失败要有日志可查，能定位 |
| 协议变更适配 | 平台升级协议会提前 30 天通知 |
| App Key 轮换 | 怀疑泄露立刻重置 |
| 下架通知 | 主动下架请提前告知，避免用户屏上突然空白 |

## 7. 附录：速查

### 7.1 接口一览

| 接口 | 方法 | 鉴权 |
|---|---|---|
| `/openapi/v1/pairing/start` | POST | App Key |
| `/openapi/v1/pairing/{code}` | GET | App Key |
| `/openapi/v1/devices/{id}/content` | POST | App Key + 已授权 |

### 7.2 状态码

| HTTP | 含义 | 怎么办 |
|---|---|---|
| 202 | 已入队 | 正常 |
| 401 | App Key 错 | 检查或重置 |
| 403 | 设备未授权 / 已撤销 | 让用户重新授权 |
| 404 | 码或设备不存在 | 重新绑定 |
| 410 | 码过期 | 重新申请 |
| 429 | 推太频 | 降频 |
