## FPC2 三色屏"开机能初始化、刷图 BUSY never asserted"根因与修复
- 现象（用户日志 2026-11-01）：`Init()` 开机 `FPC2 post-reset BUSY=0 -> 空闲电平=0` 且 `color panel ready`（通过）；但真正刷图 `ShowFrame()` 时 `FPC2 post-reset BUSY=1 -> 空闲电平=1`，随后 `MasterActivate` 后 `BUSY never asserted (idle=1)` 超时、双屏 B 刷屏失败。
- 根因：**BUSY 空闲电平"单点采样"是竞态的**。复位后面板先进入"忙窗口"（BUSY=忙电平）再翻转到"空闲电平"。开机时 200ms 后恰已翻到空闲(0)，刷图时 200ms 后仍卡在忙窗口(1) → 把"忙"误判成"空闲"。真空闲电平=0（本板反相板，与最早日志一致）。误判成 1 后整个 BUSY 等待逻辑反转：`PON` 后 `WaitBusy(==1)` 在"忙电平"上立即通过（面板实际还在上电）、`MasterActivate` 后 `WaitBusyCycle` 要等 BUSY 离开 1，但面板始终停 1（忙中）→ 误报 never asserted。
- 修复：`uc1679_display.cc/.h` 新增 `DetectIdleLevel()`——复位后轮询 BUSY，监测到**一次翻转且连续 ~100ms 不变**的电平即真空闲电平（最多 3s 覆盖长忙窗口）。原生板空闲=高(1)、反相板=低(0) 都正确，无需写死。`WakeAndConfigure()` 改用 `DetectIdleLevel()` 替换原单点 `gpio_get_level` 采样。
- 已确认 board 端 `ShowColorFrame`（3-color 分支，ssd2683za_s3_board.cc:284-302）已对红平面取反（SSD1683 RED RAM 0=红、1=无红，生成端 1=红标记），点亮后红不会反。
- 验证：需本地 `idf.py build`；预期刷图日志出现 `FPC2 空闲电平=0 (复位后稳定采样)` + `Color full refresh complete`，B 屏点亮且红区正确。若仍报 `PON 未使 BUSY 回落空闲` 才是真硬件（座子/3.3V/BUSY 接线）。

- 两项未验证过的关键修复（`uc1679_display.cc/.h`）：
  1. **恢复显式 PWR(0x01) 5 字节** `{0x03,0x00,0x2B,0x2B,0x03}`（上一轮误删）。原因：开机冷启动靠 OTP 默认电源能上电；但**从深睡唤醒后内部电源配置复位**，仅靠 OTP 无法可靠重启电荷泵 → PON 后 BUSY 不翻转、MasterActivate 不启动波形。每轮都显式发 PWR 解决。

## FPC2 B屏"动都不动"真正根因：本板 BUSY(GPIO12) 根本不连到面板 BUSY 输出，恒为 0
- 关键铁证：`ssd1619_display.h` 第 111-114 行历史注释明确写 **"历史测试中 FPC2/GPIO12 恒为 0"**。即这块板的 FPC2 BUSY(GPIO12) 接线**不接到面板 BUSY 输出**，永远读 0、从不翻转。
- 推论：之前所有版本都用"等 BUSY 翻转"来确认面板上电(PON)/刷新(MasterActivate)完成，结果面板每次都被这个死逻辑判成"未响应" → `Init` 标记 `available_=false` → `ShowFrame` 直接跳过 → B 屏"动都不动"。前面几轮修的 PWR 字节数/PLL/CDI/极性/竞态采样全是误诊；真正的拦路虎是 BUSY 线本身无效。
- 注意：BUSY 恒 0 不等于面板没电——座子探测 `FPC2/GPIO12 电平=0 驱动=是`，且面板能驱动该线（拉低），说明面板有电、活着；只是 MCU 侧的 BUSY 读不到它的忙状态。SPI 总线与 FPC1(SSD1619) 共用且 FPC1 正常，CS=GPIO9 与 FPC1 同 FPC 座定义，故 SPI 命令应可达面板。
- **修复（`uc1679_display.cc/.h`）：BUSY 握手改为容错 + 固定延时兜底。**
  - 新增 `WaitBusyTolerant(assert_timeout, idle_timeout, fixed_delay_ms)`：BUSY 在 assert_timeout 内出现翻转→精确等待回落；若始终不翻转（本板常态）→ 走 `fixed_delay_ms` 固定延时并**假定完成、返回 true**（不再判失效）。
  - `WakeAndConfigure`：删掉"复位未翻转就重试硬件复位"的无用分支；PON 后改 `WaitBusyTolerant(5000,8000,200)`（200ms 固定兜底上电）。不再因 BUSY 不翻转而 return false。
  - `ShowFrame`：`MasterActivate` 后改 `WaitBusyTolerant(2000,30000,15000)`（15s 固定兜底覆盖 400x300 三色全刷）。`Init` 因此标记 `available_=true`，每轮刷新都真正发命令+写 RAM+启动全刷。
  - `DetectIdleLevel` 轮询窗口从 3s 缩到 1s（仅用于日志/极性记录，不再决定成败）。
- 验证：本地 `idf.py build`。预期日志：`SSD1683-compatible color panel ready` + 刷图 `Color full refresh complete` + `双屏 B 已刷新`，B 屏真实点亮且红区正确（board 端已对红平面取反）。若仍"无显示但日志报 complete" → 才是真硬件（CS=GPIO9 未接对 / 面板 DOA），需查 FPC2 座子 CS 针与面板焊接。

## ⚠️ FPC2 B屏"日志报 complete 但屏完全不闪"真正根因：初始化命令序列与官方不符（非 BUSY、非硬件）
- 最新日志（2026-11-01 上午）：BUSY 容错修复后 `Init` 通过 `available_=true`，刷图 `Color full refresh complete` + `双屏 B 已刷新`，但 **B 屏物理上完全不闪、无显示**。firmware 以为刷完了，屏却一点不动——这是"命令发出但面板不执行刷新波形"的典型。

- **拿到 Waveshare 官方权威源码 `EPD_4in2bc.c`（同款 4.2"C 三色）逐字节对比，发现之前的方向全错：**
  1. **多发了会打乱 OTP 电源的 `PWR(0x01)` 5 字节电源命令**——这是真凶。官方 demo 初始化**只发** `BTST(0x06:17 17 17) → PON(0x04) → PSR(0x00:0x0F)`，**完全不发送** PWR/RES/VCOM/CDI，直接沿用面板 OTP 默认值即可上电显示。我强制写一组 PWR 值，反而打乱 OTP 默认电荷泵配置 → 面板"收到命令但电荷泵不起振、不启动刷新波形" → 屏完全不闪。
  2. **RED 极性判反**：之前让 board 端对红平面取反（以为 SSD1683 RED RAM 0=红）。但官方 `EPD_4in2bc_Display` 直接发送 `ryimage` 不取反，且 `ryimage` 中 **1=红、0=非红**。取反会导致整屏泛红。
- **本次修复（`uc1679_display.cc/.h` + `ssd2683za_s3_board.cc`），严格对齐官方 `EPD_4in2bc.c`：**
  - `WakeAndConfigure`：删掉 PWR(0x01)/RES(0x61)/VCOM(0x82)/CDI(0x50)，只剩官方三条 `BTST→PON→PSR`。
  - `HardwareReset`：对齐官方 RST 时序（高 200ms→低 2ms→高 200ms）。
  - `Sleep`：对齐官方，先 `POWER_OFF(0x02)` 再 `DEEP_SLEEP(0x07)+0xA5`（本板 BUSY 不翻转，省略 POWER_OFF 后的 ReadBusy）。
  - `ShowFrame`：0x10(BW,不取反) + 0x13(RED,不取反) + 0x12(刷新) + 固定延时 5s 兜底（覆盖 400x300 三色全刷）。
  - board 端 `ShowColorFrame` 3-color 分支：**删掉红平面取反**，直接送显（官方=1=红，与生成端 `ConvertJpegToBwrPlanes` 的 "1=红标记" 一致）。
  - 清理：删除已失效的 `reset_flip_seen_` 成员、未使用的命令常量（kCmdPll/kCmdCdi/kCmdVcomDc/kCmdResolution/kCmdPowerSetting）。
- **结论/纠正**：2026-11-01 09:32 那条"恢复显式 PWR 解决深睡唤醒"的结论是错的——PWR 恰恰是让屏不闪的元凶。真正的修法是"删掉多余命令、严格匹配官方序列"。BUSY 恒 0/不翻转（本板 GPIO12 不连面板 BUSY）的判断仍成立，BUSY 容错兜底保留。

## FPC2 B屏改用 SSD1681 完整初始化（用户提议"试试 ssd1681"）
- 用户最新反馈：三色屏仍完全不动，建议"试试 SSD1681，屏比较老驱动应该也老"。
- **技术澄清（重要）**：SSD1681 裸片最大只支持 200×200（xaipart 文档）；但 **4.2" 400×300 BWR 屏可以是 SSD1681/SSD1680 家族**（SSD1680 即 SSD1681 高分辨率版，同协议），命令集为 `0x24`(BW RAM)/`0x26`(RED RAM)/`0x22`+`0x20`(刷新)，与 SSD1683 的 `0x10/0x13/0x12` 完全不同。所以 "老屏=老驱动" 的直觉方向对，但 SSD1683 最小序列（依赖 OTP）对这块屏无效。
- **权威蓝本**：QYEG0420BNS19AF0（4.2" 400×300 B/W/Red，SSD1681 家族）规格书"LUT from OTP"参考程序：软复位 0x12 → 0x74/0x7E 模拟/数字块 → 0x2B VCOM → 0x0C Booster → 0x01 驱动输出(300行) → 0x11 入口模式 → 0x44/0x45 RAM 窗口 → 0x3C 边框 → 0x18 温度传感器 → 0x22+0xB1 加载 OTP LUT → 0x20 主激活；刷图：0x4E/0x4F 设 RAM 计数器 → 0x24 写 BW → 0x26 写 RED → 0x22+0xC7 → 0x20 刷新。
- **改动（`uc1679_display.cc/.h`）**：两套驱动共存、编译期宏 `FPC2_DRIVER_SSD1681`（默认 1）分派。
  - SSD1681 路径：完整显式初始化（上述序列），红平面 0x26、BW 0x24，深睡 0x10+0x01；LUT 走 OTP（0x22+0xB1）。
  - SSD1683 路径：保留上一轮最小 OTP 序列作为一键回退（宏置 0）。
  - 命令帧（CS 全程低）沿用本板已验证写法；BUSY 仍走 WaitBusyTolerant 固定延时兜底（本板 GPIO12 不连面板 BUSY）。
  - 平面格式不变：bw 1=白/0=黑，red 1=红/0=非红（SSD1681 与 SSD1683 约定一致，board 端无需再取反）。
- **关键纠错**：GxEPD2 的 `GxEPD2_420c` 标注为 "GDEW042Z15 400x300, UC8176 (IL0398)"——即 Waveshare 4.2"B 老款控制器是 UC8176/SSD1683 兼容（命令集 0x10/0x13），而部分 4.2" 三色屏（如 QYE 系）走 SSD1681 命令集（0x24/0x26）。两套都存在于 4.2" 三色市场，故做成可切换。
- 验证：本地 `idf.py fullclean && idf.py build && 烧录`。预期日志出现 `SSD1681 三色面板就绪` + `Color full refresh complete`，B 屏真实点亮。若仍不动：① 把 `FPC2_DRIVER_SSD1681` 置 0 回退 SSD1683；② 若两者都不行才是真硬件（CS=GPIO9 座子/焊接/DOA 或面板 OTP LUT 未烧——QYE 参考依赖 OTP LUT，若面板 OTP 空则需显式下发 70 字节 LUT）。

## 🔥 B 屏雪花噪点根因（2026-11-01 收尾，对照 Waveshare 官方 EPD_4in2b_V2.c 后定位）
- **对照权威源码结论**：Waveshare NEW `Display_new` 写 `0x24`(BW) **不取反**、写 `0x26`(RED) **取反**(`~ryimage`)；与我驱动一致 → 数据极性没错。NEW init 含 0x12软复位/0x3C/0x18/0x11/0x44-0x45/0x4E-0x4F，**不发 PON/PSR**（soft-reset 后隐含上电）——我之前 NEW 里多发 0x04 PON+0x00 PSR 属冗余但不致命。
- **雪花噪点真凶 = 刷新未完成就发深睡命令破坏 RAM**：日志时间线 `Color full refresh complete`(59841) 之后 8000ms `BUSY 超时 8000ms(GPIO12=1)` 仍在 BUSY 高 → 说明 `ActivateAndWait` 返回时**刷新波形还没跑完**，紧接着 `Sleep()` 立刻下发 `0x50/0x02/0x07`(断电+深睡) 给仍在刷新的面板 → RAM 被冲成乱码 = 雪花噪点。
- **三色全刷（含红通道）很慢，典型 12~15s**：旧超时 8s/20s 远不够，导致 BUSY 永远"超时"→ 触发上面的破坏。
- **本次修复（已落地 `uc1679_display.cc`，待烧录）**：
  - `Sleep()` 改为**先 `WaitBusy(30s)` 等 BUSY 真正回落再发深睡命令**；若仍忙（刷新没完）则**跳过深睡、保留当前画面**（代价仅多耗电，远比破坏显示好）。这是消除噪点的关键。
  - `kRefreshBusyTimeoutMs` 20000→**30000**；`Init` 探测帧的 `ActivateAndWait` 也改用 30s 超时（不再用 8s 探测超时）。
  - `ActivateAndWait` 维持"发刷新命令即返回 true(最佳努力)"，但前面已等 4s+WaitBusy。
- **数据链路已验证无问题**：`inksight_client.cc:889-923` 把 2bpp 拆成 bw(1=白)/red(1=红) 两平面正确；板级 `ShowColorFrame` 把真实 `color_bw_/color_red_` 传给 `Uc1679Display::ShowFrame`。A 屏同数据正常 → 数据非噪点来源。
- **待验证**：用户断电重启+烧录后，预期 B 屏显示真实课程表（含红字/红块），不再雪花。若仍噪点 → 才需怀疑刷新命令本身在面板上不完成（BUSY 永不落），届时查 NEW 序列 0x22/0x20 参数或窗口 0x44/0x45 方向（当前 Y 窗口 {0x2B,0x01,0x00,0x00} 与 Waveshare {0x00,0x00,0x2B,0x01} 相反，仅影响上下翻转、不产生噪点，暂不改以免回退）。

## 🔥🔥 B 屏雪花真凶落定（推翻 178-187 节「刷新被打断」结论）
- **用户 16:11 实测日志**：Sleep() 改"等 BUSY 再深睡"后，B 屏仍"闪两下→雪花"。关键线索：日志 `BUSY 超时 8000 ms (GPIO12=1, 有效电平=1)`——这个 8000 来自 `Sleep()` 里**深睡命令之后**的 `WaitBusy(kProbeBusyTimeoutMs)`，说明**第一句 `WaitBusy(30000)` 已成功返回（刷新确实跑完了）、深睡命令也确实下发**。→ 推翻"刷新被打断"假设：波形正常执行，但**写进 RAM 的画面是乱码** → 根因转向数据/寻址/序列与面板不符。
- **抓到 Waveshare 官方权威源码 `EPD_4in2b_V2.c`（flag==0=NEW/UC8176，正是本板）逐字节比对，发现 3 处真错**：
  1. **⚠️ Y 窗口 + RAM 计数器字节序全反（雪花直接元凶）**：我 `k81RamYData={0x2B,0x01,0x00,0x00}`（start=299>end=0，退化窗口）、`k81RamYCntr={0x2B,0x01}`（Y 计数器起点=299）。官方 NEW：`0x45={0x00,0x00,0x2B,0x01}`（Y 起点0/终点299）、`0x4F={0x00,0x00}`（Y 计数器起点0）。**之前我误判"只影响上下翻转"是错的**——start>end 的退化窗口让写地址越出有效区、数据落进未初始化 RAM = 雪花。已改为官方值。
  2. **RED 极性判反（取反反而整屏泛红）**：我 `SendImagePlanes` 对红平面 `invert_data=true`。但 `album_photo.cc:34-35,65-71` 铁证 `red_plane` 预填 0x00、红像素置位 = **1=红**；board:284-286 注释也明确"三色路径直接送显、无需取反（取反反而整屏泛红）"。官方 `Display_new` 取反 `~ryimage` 是因为**它输入是 0=红**；我们输入 1=红，故**必须不取反**才能得 RED RAM 1=红。已去掉红通道取反（OLD/NEW 均改 `invert_data=false`）。
  3. **NEW 变种深睡命令错**：我 `Sleep()` 两变种都用 OLD 序列 `0x50/0x02/0x07`。官方 NEW `Sleep_new=0x10/0x03`。已改 `Sleep()` 按 `variant_` 分支（OLD 走旧序列、NEW 走 `0x10/0x03`）。
- **加固**：NEW init 软复位 `0x12` 后补 `WaitBusy(kProbeBusyTimeoutMs)`（对齐官方 0x12 后 ReadBusy）。NEW init 的 `0x04(PON)+0x00(PSR=0x0F)` 保留（官方 NEW 省略但本板良性，且非雪花成因）。
- **数据链路已二次确认非雪花源**：`color_bw_/color_red_` 由 `ConvertJpegToBwrPlanes`（board:771）填真实课程表；`inksight_client.cc:889-923` 的 2bpp→bw/red 拆包（bw 1=白/red 1=红）正确。A 屏同数据正常。
- **已落地待烧录（`uc1679_display.cc/.h`）**：① Y 窗口/计数器改官方值；② 红通道去掉取反；③ Sleep 按变种分支深睡；④ NEW 软复位后 WaitBusy。
- **验证阶梯（给用户）**：`idf.py fullclean && idf.py build && 烧录`（断电重启清软锁死）。预期：B 屏闪一下后显示**真实课程表（含红字/红块），不再雪花**。若仍异常：① 全黑/全白=数据极性；② 整屏泛红=红仍被取反；③ 上下/左右翻转但内容清晰=窗口起点终点需互换或 data-entry 方向调（非雪花，小修）；④ 仍雪花=真硬件（FPC2 座子/CS 针 GPIO9 焊接/面板 DOA）。

## 🐞 场景中心"自定义场景看不到可编排应用"根因与修复
- **现象**：用户进场景中心，点「自定义」场景卡片，下方"已上线应用"区显示"本场景暂无匹配的已上线应用"，但"已上线应用"tab 里明明有 `codex脉动`(scene=office)。
- **根因**：`presetScenes` 里存在一个**预设**场景 key=`custom`、显示名="自定义"（与用户"自定义场景"概念撞名）。用户点的是这个**预设卡片**，它不在 `customSceneKeys`（仅后端 `/api/scenes` 的用户自建场景才在里面）→ `isCustom=false` → 按 `a.scene === selected` 过滤，而 `codex脉动` 的 scene=office ≠ "custom" → 空列表。用户自建的自定义场景（走「新建」）逻辑是对的（isCustom=true 展示全部），只是命名撞了预设导致误触。
- **修复（content-console-cn + content-console 两版同步）**：
  1. 预设 `custom` 场景改名**「自由组合」**（eyebrow 改"空白画布"，A/B 标题改为"自由组合 A/B 屏"），与「新建」卡片的"自定义场景"彻底区分，消除命名混淆。
  2. 应用列表逻辑新增 `showAllApps = isCustom || selected === "custom"`：让预设「自由组合」画布**与用户自定义场景一样展示全部已上线应用**供手动编排（不再按 scene 标签过滤）。文案/空状态文案同步改为 `showAllApps` 分支。
  3. `isCustom` 仍仅用于"删除按钮"（预设不可删），不受影响。
- **验证**：8094(cn) 为 Next dev 常驻，HMR 自动生效；改动仅布尔/字符串，无类型风险。用户刷新后台即可：选「自由组合」或自建「自定义场景」都能看到并可把 `codex脉动` 设为 A/B 屏。
