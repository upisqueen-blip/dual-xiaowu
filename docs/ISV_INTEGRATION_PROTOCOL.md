# 小悟双屏 ISV 接入协议 v1.0

> 适用对象：希望把自己的应用数据显示在小悟 AI 电子墨水屏上的第三方开发者（ISV）。
> 协议版本：`v1.0`　最后更新：2026-11-02
> 平台基线：`xiaowu_platform`（单后端）+ 400×300 双屏电子墨水硬件
>
> **机器可读版（推荐写代码时优先看这个）**
> - 在线文档：`http://<平台地址>/developer/api-docs`
> - OpenAPI JSON：`GET /openapi/isv.json`（加 `?download=1` 直接下载）
> - OpenAPI YAML：`GET /openapi/isv.yaml`　·　Markdown：`GET /openapi/isv.md`
>
> 本文是设计与约束说明，字段级定义以 OpenAPI 为准；两者冲突时以代码 `xiaowu_platform/isv_spec.py` 为最终真源。

## 0. 先读这一页

### 0.1 这份协议分三层，缺一层都上不了线

| 层 | 解决什么问题 | 你做的东西 | 对应章节 |
|---|---|---|---|
| **第一层 确权** | 这条数据是**谁的**、该落到**哪块屏** | 走一次绑定，拿到 `device_id` 和授权 | 第 1 章 |
| **第二层 业务** | 数据**从哪来**、长什么样 | 一个能返回卡片 JSON 的端点 / 推送程序 | 第 2 章 |
| **第三层 渲染** | A 屏显示什么、B 屏显示什么 | 按语义槽位填内容，不是随便塞两块 | 第 3 章 |

三层是严格顺序依赖的：没有确权，推送会被 403 拒掉；没有合规契约，审核会被打回；没有双屏适配，设备上会显示不全。

### 0.2 三方角色边界（最重要的一张表）

| 角色 | 有什么 | 能做什么 | **绝对不能做什么** |
|---|---|---|---|
| **小悟平台** | 用户账号、设备、授权关系、渲染管线 | 确认归属、接收数据、出图下发 | 读取、存储、代查任何大模型账户凭证 |
| **用户** | 小悟账号、设备、各大模型账号 | 授权哪些应用可以显示在自己的屏上 | 不需要向开发者提供任何大模型密码 |
| **开发者（你）** | 自己的应用、自己的凭证来源 | 读取用户数据（在用户侧）、推送卡片 | 转存用户凭证、把凭证上传给平台 |

### 0.3 三条红线（违反直接下架）

1. **不得把用户的任何 API Key、access token、refresh token、Cookie 上传到小悟平台或你自己的服务器**（除用户本机）。
2. **不得伪造 `device_id`**，不得对未获授权的设备推送内容。
3. **不得在卡片数据里夹带用户隐私原文**（对话内容、文件路径、邮箱、手机号）。

平台侧只有一个凭证概念：**你自己的应用凭证（App Key）**。它标识“你是哪个应用”，不标识“你是哪个用户”。

## 1. 第一层：确权（Auth & Binding）

### 1.1 先分清两个完全不同的“账号”

开发者最常在这里搞混，一旦混淆，整个接入方案就会走错方向。

| | 大模型账号（ChatGPT / Codex / DeepSeek / Claude…） | 小悟账号 |
|---|---|---|
| 归属 | 用户个人 | 用户在小悟平台注册的账号 |
| 凭证在哪 | **只在用户自己手里**（如 `~/.codex/auth.json`） | 平台签发会话 token |
| 平台能否访问 | ❌ 永远不能 | ✅ 平台自己发的 |
| 用途 | 查用户自己的额度/用量 | 确认“这台设备是谁的” |

**确权层只处理第二列，永远不处理第一列。**

平台的职责边界是一句话：

> 平台负责回答「**这条数据可以显示在哪块屏上**」，不负责回答「**这个用户的余额是多少**」。

前者是授权问题，后者是取数问题。取数发生在你的应用侧（最好在用户本机），平台只接收结果。

### 1.2 为什么用绑定码，而不是让用户填账号密码

| 方案 | 违规风险 | 泄露风险 | 用户成本 | 结论 |
|---|---|---|---|---|
| 用户把大模型账号密码给平台 | 高（违反各家条款） | 极高 | 低 | ❌ 禁止 |
| 用户把 API Key 填到平台后台 | 中（平台成为凭证保管方） | 极高（库泄露=全部被盗） | 低 | ❌ 禁止 |
| **一次性绑定码（本协议采用）** | 无 | 无（凭证从不出用户机器） | 低（输 6 位码） | ✅ 采用 |

绑定码即 RFC 8628 Device Authorization Grant，也就是电视上“登录 Netflix，输入屏幕上的 6 位码”那套流程，用户已经熟悉。

**为什么不能用 MAC 地址做钥匙**：MAC 可伪造、可枚举、会被隐私扫描收集。本平台中 `device_id` 恰好是 MAC 格式（如 `DC:DA:0C:44:6D:D4`），但它**只作为标识符**，鉴权一律走 `device_token` 或授权记录。你的应用**不应该、也不需要**自己采集 MAC。

### 1.3 绑定流程（4 步）

```
你的应用                     小悟平台                      用户
   |                            |                            |
   |-- ① 申请绑定码 ----------->|                            |
   |<-- code=K7M-2QP (10分钟) --|                            |
   |                            |                            |
   |-- ② 展示码给用户 ---------------------------------------->|
   |                            |<-- ③ 登录后台/App 输入码 ---|
   |                            |    选择要授权的设备         |
   |                            |    确认授权                 |
   |                            |                            |
   |-- ④ 轮询取 device_id ------>|                            |
   |<-- approved + device_id ----|                            |
   |                            |                            |
   |-- ⑤ 推数据（带 device_id）->|  校验授权 → 入队 → 设备出图 |
```

关键点：

- 第 ③ 步**必须由已登录的用户完成**，这一步才建立“用户 ↔ 设备”的归属。你的应用无法代替用户做这一步，这是安全的根基。
- 你的应用拿到的是 `device_id`，**拿不到 user_id、拿不到用户任何凭证**。
- 授权是**可撤销**的：用户在后台点一下撤销，你的推送立刻 403。

### 1.4 API：第一步 申请绑定码

```http
POST /openapi/v1/pairing/start
X-App-Key: <你的应用凭证>
Content-Type: application/json

{
  "label": "张三的 MacBook Pro",
  "scopes": ["device.content.write"]
}
```

响应 `201`：

```json
{
  "code": "K7M2QP",
  "display_code": "K7M-2QP",
  "expires_in": 600,
  "verify_url": "http://<平台地址>/pair?code=K7M-2QP",
  "poll_interval": 3
}
```

- `code`：后续轮询用（不带连字符）
- `display_code`：展示给用户输入（带连字符，去掉易混字符 `0/O/1/I`）
- 有效期 **10 分钟**，一次性，用过即失效
- `poll_interval`：建议轮询间隔（秒），不要低于 3 秒

**`label` 必填且要真实**：它会显示在用户的授权列表里，写成“设备1”用户不敢授权。

### 1.5 API：第二步 轮询绑定结果

```http
GET /openapi/v1/pairing/K7M2QP
X-App-Key: <你的应用凭证>
```

四种状态：

```json
{ "status": "pending" }
{ "status": "approved", "device_id": "DC:DA:0C:44:6D:D4", "grant_id": "grant-3f9a1c2d" }
{ "status": "denied",   "reason": "用户拒绝了授权" }
{ "status": "expired" }
```

- `expired` 之后**不要复用这个码**，重新走 1.4 申请新码
- 拿到 `approved` 后**立刻停止轮询**，把 `device_id` 和 `grant_id` 存到你自己的配置里
- `device_id` 是长期有效的，除非用户在平台上撤销授权

### 1.6 API：用户侧（平台提供，你不用实现）

以下接口由小悟后台/App 调用，列出来是让你知道用户在做什么，便于对齐产品设计：

| 接口 | 作用 |
|---|---|
| `GET /api/v1/mobile/pairing/{code}` | 展示“哪个应用申请授权、申请什么权限、我有哪几台设备” |
| `POST /api/v1/mobile/pairing/{code}/confirm` | 用户选定设备并确认，body `{"device_id":"..."}` |
| `POST /api/v1/mobile/pairing/{code}/deny` | 用户拒绝 |
| `GET /api/v1/mobile/grants` | 用户查看自己所有已授权应用 |
| `DELETE /api/v1/mobile/grants/{grant_id}` | 用户撤销某条授权（**你的推送会立刻失效**） |

### 1.7 权限（Scope）清单

| Scope | 能做什么 | 说明 |
|---|---|---|
| `device.content.write` | 向已授权设备推送卡片内容 | 核心权限，必须申请 |
| `device.read` | 读取设备型号/能力/在线状态 | 用于自适应（如四色屏才用红/黄） |
| `device.event.read` | 读取设备事件（已显示/失败回执） | 用于闭环确认，建议申请 |

**最小权限原则**：只申请你真正要用的。多申请的会在审核时被要求说明理由。

### 1.8 你的凭证怎么保管

```json
{
  "app_key": "存到系统钥匙串 / 环境变量，不要写进 Git",
  "device_id": "DC:DA:0C:44:6D:D4",
  "grant_id": "grant-3f9a1c2d"
}
```

- App Key 泄露 = 别人可以冒充你的应用推送（但仍受授权限制，推不到未授权的设备）
- 发现泄露立刻在开发者后台重置 App Key
- **不要**把 App Key 硬编码在前端 / 可执行文件明文 / 公开仓库里

### 1.9 常见错误

| 现象 | 原因 | 处理 |
|---|---|---|
| `401 invalid app key` | App Key 错误或已停用 | 检查 / 重置 |
| `403 device_not_granted` | 该设备未授权给你的应用 | 让用户重新走绑定码流程 |
| `404 pairing_not_found` | 码不存在或已被使用 | 重新申请 |
| `410 pairing_expired` | 超过 10 分钟 | 重新申请 |
| `409 pairing_already_used` | 该码已被确认过 | 重新申请 |

## 2. 第二层：业务（数据获取与投递）

### 2.1 两种投递模式，选一种

| | **Push（推荐）** | **Pull** |
|---|---|---|
| 谁发起 | 你的应用主动推给平台 | 平台定时来拉你的端点 |
| 适用 | 数据在用户本机 / 你家里 NAT 后面 | 你有稳定公网服务端 |
| 平台要求 | 你的端点可不公网，只要能出网 | 你的端点必须公网可达、稳定、低延迟 |
| 典型 | **Codex 脉动这类桌面应用** | SaaS 型服务 |
| 本协议 | ✅ 主推 | ✅ 支持 |

**重要**：跑在用户个人电脑上的应用（NAT 后面、动态 IP），**只能用 Push**。平台没有公网地址去访问你家里的机器。

### 2.2 Push：推送卡片

```http
POST /openapi/v1/devices/DC:DA:0C:44:6D:D4/content
X-App-Key: <你的应用凭证>
Content-Type: application/json

{
  "template": "eink-card-v1",
  "screens": {
    "A": {
      "title": "API 额度",
      "subtitle": "Codex",
      "items": [
        { "label": "剩余额度", "value": "$42.10", "emphasis": "red" },
        { "label": "到期倒计时", "value": "6 天" },
        { "label": "本月用量", "value": "68%", "progress": 68 }
      ],
      "footer": "更新于 17:08"
    },
    "B": {
      "title": "重置预告",
      "subtitle": "未来 7 天",
      "items": [
        { "label": "预计重置", "value": "11-08 09:00" },
        { "label": "当前周期", "value": "第 3 天" },
        { "label": "昨日消耗", "value": "+9%" }
      ],
      "footer": "数据来源：本机读取"
    }
  },
  "expires_in_seconds": 900
}
```

响应 `202`：

```json
{ "task_id": "task-8a1b", "status": "queued" }
```

- `screens` 里 **A / B 可只给一个**，另一个保持设备当前内容
- 想两屏显示同一份内容，用 `"screens": { "A": {...}, "B": {...} }` 各写一份，或旧格式 `{"template":"eink-card-v1","screen":"both","data":{...}}`
- `expires_in_seconds`：**建议 900~3600**。卡片是“快照”，过期后设备回落到用户自己的场景配置，避免显示一周前的旧余额骗人

### 2.3 卡片数据契约 v1

```jsonc
{
  "title":    "string, 1-24 字符, 必填",       // 卡片主标题
  "subtitle": "string, 0-32 字符, 可选",       // 来源/时间范围
  "items":    "array, 1-6 项, 必填",           // 数据行
  "footer":   "string, 0-40 字符, 可选",       // 数据来源、更新时间
  "qr":       "string, 可选",                  // 绝对 URL 才出二维码，相对路径只显示文本
  "refresh_minutes": "int, 5-1440, 可选"       // 建议刷新间隔，平台用于节流
}
```

`items[]` 每一项：

```jsonc
{
  "label":    "string, 1-12 字符, 必填",   // 指标名，如「剩余额度」
  "value":    "string, 1-16 字符, 必填",   // 值，如「$42.10」
  "hint":     "string, 0-16 字符, 可选",   // 补充说明，小字
  "progress": "int, 0-100, 可选",          // 有则渲染进度条
  "emphasis": "red | yellow | none, 可选"  // 强调色，仅四色屏有效
}
```

**硬约束（超出会被校验拦下）**：

| 项 | 限制 | 原因 |
|---|---|---|
| 总大小 | ≤ 32 KB | 设备内存与传输 |
| `items` 数量 | 1–6 | 400×300 放不下更多 |
| `title` | ≤ 24 字符 | 超了截断 |
| `items[].value` | ≤ 16 字符 | 超了截断且很难看 |
| 数值精度 | 百分比取整 | 墨水屏无小数可读性 |

### 2.4 多模型（provider）怎么表达

**不要**为每个模型做一张卡。**一张卡里用 `label` 承载 provider 名**即可：

```json
{
  "title": "账户总览",
  "subtitle": "3 个服务",
  "items": [
    { "label": "Codex",     "value": "68%",    "progress": 68, "emphasis": "red" },
    { "label": "DeepSeek",  "value": "¥42.10" },
    { "label": "Claude",    "value": "正常" },
    { "label": "WorkBuddy", "value": "已续期" }
  ],
  "footer": "本机读取 · 17:08"
}
```

**但这里有个业务边界必须讲清**：

- 你的应用**只能读到你被授权、且你能拿到凭证的那些服务**。Codex 脉动读不到用户的 DeepSeek 余额，除非用户也在你这里配置了 DeepSeek。
- 想“一块屏显示全部模型”，有两条路：① 你的应用做聚合（用户在你这里配置多个服务）；② 用户装多个 ISV 应用，各自推各自的卡片，设备按场景轮播。
- **平台不会替你跨应用抓数据**。这是安全边界，不是能力缺失。

### 2.5 刷新与容错

| 场景 | 要求 |
|---|---|
| 推送频率 | 建议 ≥ 5 分钟一次；平台按 `refresh_minutes` 做节流，过频会被忽略 |
| 设备离线 | 平台会入队，设备上线后取最新一条；旧卡片按 `expires_in_seconds` 过期 |
| 你取数失败 | **不要推占位数据**（如 0、"--" 冒充真实值）。宁可推一份带 `hint: "取数失败"` 的说明卡，或干脆不推 |
| 数值未知 | 用 `"value": "待确认"`，不要写 `0`。墨水瓶上假数据比没有数据更有害 |
| 时间显示 | 统一北京时间，格式 `MM-DD HH:mm` |

### 2.6 Pull：如果你坚持要平台来拉

```http
GET https://your-server/api/eink-card?screen=A
Authorization: Bearer <你签发给平台的 token>
```

要求：

- 响应时间 ≤ 3 秒（超时视为失败）
- 返回 2.3 的卡片 JSON
- 必须支持 `?screen=A|B` 区分双屏
- 端点必须是公网可达的 HTTPS
- 平台会按 `refresh_minutes` 轮询，不要依赖实时触发

> Pull 模式当前用于平台侧的“数据接口”轨（开发者后台配置端点 + 样本 JSON），与 Push 并存。

## 3. 第三层：双屏渲染

### 3.1 硬件事实（决定了你必须怎么设计）

| 项 | 规格 |
|---|---|
| 屏幕 | 双屏物理独立，A 屏 + B 屏 |
| 分辨率 | 400×300（部分型号 648×480 / 800×480） |
| A 屏 | 黑白双色（1-bit），**没有红色** |
| B 屏 | 四色：黑 / 白 / 红 / 黄 |
| 刷新 | 慢（秒级），全刷会闪烁，**不适合高频跳动** |
| 固件能力 | **不渲染 HTML / CSS**，只显示服务端生成的位图 |

**最重要的一条**：固件不跑浏览器。所以你交的不是网页，是**结构化数据**，由平台按模板画成位图。

### 3.2 A / B 屏语义槽位

不要随便塞两块内容。按语义分工，用户才看得懂：

| 屏 | 语义 | 该放什么 | 不该放什么 |
|---|---|---|---|
| **A 屏** | **此刻的状态** | 主指标、百分比、剩余量、是否告警 | 长列表、趋势、历史 |
| **B 屏** | **接下来会怎样** | 趋势、倒计时、下次重置、预测 | 重复 A 屏的数字 |

以 Codex 额度为例：

| | A 屏（现在） | B 屏（未来） |
|---|---|---|
| 标题 | API 额度 | 重置预告 |
| 内容 | 剩余 $42.10 / 用量 68% / 到期 6 天 | 预计 11-08 重置 / 周期第 3 天 / 昨日 +9% |
| 强调色 | 低于 20% 用红 | 重置临近用黄 |

**判定标准**：A 屏回答“我现在还有多少”，B 屏回答“我什么时候能恢复 / 会耗尽吗”。两块内容**互不重复**。

### 3.3 排版约束（平台校验会拦）

| 约束 | 值 | 原因 |
|---|---|---|
| 正文字号 | ≥ 18 px | 墨水屏 DPI 低，小字糊 |
| 一屏数据行 | ≤ 4 行（A 屏）/ ≤ 4 行（B 屏） | 300px 高度 |
| 标题长度 | ≤ 12 个中文 | 超了换行破坏版式 |
| 颜色 | A 屏只用黑/白；B 屏只用黑/白/红/黄 | 硬件色域 |
| 动画 | **禁止** | 墨水屏不刷新动画 |
| 渐变/阴影 | 禁止 | 四色无法还原，出图变脏块 |

### 3.4 服务端会替你做的自适应

- `emphasis: "red"` 在 **A 屏自动降级**为黑色加粗（A 屏无红）
- `progress` 在进度条末端用强调色填充
- 长文本自动折行 + 省略号
- 未提供 `B` 时，B 屏保持原内容不变

### 3.5 提交前必须自检

在开发者后台「我的应用」里：

1. 点「**设备出图预览**」→ 看 A/B 两屏真实位图
2. 检查：文字是否被截断、`value` 是否超 16 字符、A 屏红色是否已降级
3. 检查：B 屏内容是否只是重复 A 屏（是的话重新设计）
4. 确认无误再提交审核

预览用的是**和设备完全同源的渲染管线**，看到什么，屏上就是什么。

## 4. 提交与审核

### 4.1 提交清单

审核会被逐项核对，缺一项打回：

| # | 项 | 要求 |
|---|---|---|
| 1 | 应用信息 | 名称、简介（≤100 字）、归属场景 |
| 2 | **确权实现** | 走通绑定码流程，能正确保存 `device_id` + `grant_id` |
| 3 | **数据来源说明** | 数据从哪来（本机读 / 你自己的服务端），是否涉及第三方凭证 |
| 4 | **凭证处理声明** | 明确声明“不转存、不上传用户大模型凭证” |
| 5 | **双屏适配** | A/B 两屏语义不重复，通过 3.3 全部约束 |
| 6 | **出图预览** | 提供 A/B 两屏预览截图 |
| 7 | 容错说明 | 取数失败 / 未知值 / 设备离线时怎么表现 |
| 8 | 刷新策略 | 推送频率、`expires_in_seconds` 取值理由 |

### 4.2 审核流程

```
提交 → 自动校验（schema / 尺寸 / 字号 / 凭证声明）
     → 人工审核（语义合理性、隐私、双屏设计）
     → 通过 → 登记到「已上线应用」→ 用户可在场景中心编排
     → 驳回 → 附具体原因 → 修正后重新提交
```

### 4.3 上线后

- 你的应用会出现在用户的「已上线应用」和「场景中心」，标注 **`ISV提供`**
- 用户可以把它配到 A/B 屏，也可以放进自定义场景
- 用户撤销授权后，你的推送立即 403，**且不会再自动恢复**，需要用户重新绑定

## 5. 最小可运行示例（Python）

一个完整的“确权 → 推送”最小实现，可直接改造：

```python
import time, requests

BASE = "http://127.0.0.1:8104"
APP_KEY = "你的应用凭证"

def start_pairing():
    r = requests.post(f"{BASE}/openapi/v1/pairing/start",
                      headers={"X-App-Key": APP_KEY},
                      json={"label": "我的 MacBook", "scopes": ["device.content.write"]},
                      timeout=10)
    r.raise_for_status()
    p = r.json()
    print(f"请在 https://你的小悟后台/pair 输入：{p['display_code']}")
    return p

def wait_for_device(code, interval=3, timeout=600):
    deadline = time.time() + timeout
    while time.time() < deadline:
        r = requests.get(f"{BASE}/openapi/v1/pairing/{code}",
                         headers={"X-App-Key": APP_KEY}, timeout=10)
        s = r.json()
        if s["status"] == "approved":
            print("已授权设备：", s["device_id"])
            return s["device_id"]
        if s["status"] in ("denied", "expired"):
            raise RuntimeError(f"授权失败：{s['status']}")
        time.sleep(interval)
    raise TimeoutError("等待授权超时")

def push(device_id, card_a, card_b):
    r = requests.post(f"{BASE}/openapi/v1/devices/{device_id}/content",
                      headers={"X-App-Key": APP_KEY},
                      json={"template": "eink-card-v1",
                            "screens": {"A": card_a, "B": card_b},
                            "expires_in_seconds": 900},
                      timeout=10)
    r.raise_for_status()
    return r.json()

if __name__ == "__main__":
    p = start_pairing()
    dev = wait_for_device(p["code"])
    push(dev,
         {"title": "API 额度", "subtitle": "Codex",
          "items": [{"label": "剩余额度", "value": "$42.10", "emphasis": "red"},
                    {"label": "本月用量", "value": "68%", "progress": 68}],
          "footer": "本机读取 · 17:08"},
         {"title": "重置预告",
          "items": [{"label": "预计重置", "value": "11-08 09:00"},
                    {"label": "当前周期", "value": "第 3 天"}],
          "footer": "未来 7 天"})
```

## 6. 附：错误码总表

| HTTP | code | 含义 | 你该做什么 |
|---|---|---|---|
| 400 | `invalid_payload` | 卡片字段不合契约 | 按 2.3 修正 |
| 401 | `invalid_app_key` | 应用凭证错/停用 | 检查或重置 |
| 403 | `device_not_granted` | 设备未授权给你 | 走绑定码流程 |
| 403 | `grant_revoked` | 用户已撤销 | 请用户重新授权 |
| 403 | `missing_scope` | 缺权限 | 后台申请 scope |
| 404 | `pairing_not_found` | 码不存在 | 重新申请 |
| 404 | `device_not_found` | device_id 无效 | 重新绑定 |
| 409 | `pairing_already_used` | 码已用过 | 重新申请 |
| 410 | `pairing_expired` | 码过期（10 分钟） | 重新申请 |
| 413 | `payload_too_large` | 超 32 KB | 精简数据 |
| 422 | `template_validation_failed` | 必填字段缺失 | 补字段 |
| 429 | `rate_limited` | 推送过频 | 按 `refresh_minutes` 降频 |
